# 酒店级采集流程 v2 冻结稿

本文件是当前酒店采集后续开发的准入规则。

后续涉及酒店采集、单酒店诊断、小放量、40 家放量、销售输出的数据生成逻辑，必须先遵守本规则。

## 一、核心口径

主口径只看：

`大床有早餐`

其他口径不是硬门槛，只做顺手采集：

- 大床无早餐
- 双床有早餐
- 双床无早餐

最终销售输出的硬条件是：

四个平台都确认同店，并且四个平台都有 `大床有早餐` 价格。

## 二、校准测试模式

目的：

不是产出销售结果，而是验证链路稳定性、平台表现、失败原因和截图留痕是否可靠。

流程：

1. 青猫锁定 1 家酒店  
   记录酒店名、城市、地址、门牌号、截图。

2. 青猫读取主口径  
   先找 `大床有早餐`。

3. 青猫没有主口径  
   记录失败，保存截图。  
   这家酒店结束，换下一家。

4. 青猫有主口径  
   继续跑阿里、在途、携程。

5. 校准模式不启用 fail-fast  
   即使阿里失败，也继续跑在途和携程。  
   目的是统计每个平台真实表现。

6. 每个平台进入同店详情页后  
   先确认同店：同城市 + 同门牌号。  
   确认同店后，先读取主口径：`大床有早餐`。

7. 同时顺手读取其他可见口径  
   有就记录，没有就留空。  
   其他口径不影响主口径判断。

8. 每个平台必须记录字段：

- 是否同店
- 同店判断依据
- 平台酒店名
- 平台地址
- 平台门牌号
- 是否有主口径
- 主口径价格
- 大床无早餐价格
- 双床有早餐价格
- 双床无早餐价格
- 耗时
- 失败类型
- 失败原因
- 截图路径
- finalUrl
- 页面文本摘要

9. 校准模式输出结论  
   每家酒店都要输出完整诊断结果。  
   即使某个平台失败，也不能静默跳过。

## 三、生产采集模式

目的：

高效率拿到可进入销售输出的数据。

平台顺序暂定：

`青猫 → 阿里 → 在途 → 携程`

原因：

阿里和在途历史失败率更高，应更早做淘汰。  
携程相对稳定，放最后补齐。

流程：

1. 青猫锁定 1 家酒店  
   记录酒店名、城市、地址、门牌号、截图。

2. 青猫读取 `大床有早餐`  
   没有价格，直接放弃这家酒店，换下一家。

3. 青猫有 `大床有早餐`  
   继续查竞品。

4. 查阿里  
   先确认同城市 + 同门牌号。  
   再读取 `大床有早餐`。

5. 阿里失败则放弃  
   包括：

- 无法确认同店
- 同店但无大床有早餐
- 页面加载失败
- 登录失效
- 日期/城市错误
- 解析疑似失败

6. 阿里成功后查在途  
   同样先确认同店，再读取主口径。

7. 在途失败则放弃  
   规则同阿里。

8. 在途成功后查携程  
   同样先确认同店，再读取主口径。

9. 携程失败则放弃  
   规则同阿里。

10. 四个平台都成功  
    这家酒店进入最终销售输出。

11. 其他口径顺手采集  
    每个平台进入同店详情页后，如果页面上能读到：

- 大床无早餐
- 双床有早餐
- 双床无早餐

就记录。  
读不到就留空。  
不影响这家酒店是否进入最终销售输出。

12. 被放弃酒店必须留痕  
    必须记录失败类型、失败原因、截图路径、finalUrl、页面文本摘要。  
    不能静默跳过。

## 四、放弃规则

| 场景 | 生产模式处理 | 校准模式处理 |
|---|---|---|
| 青猫无大床有早餐 | 放弃酒店，换下一家 | 记录失败，换下一家 |
| 阿里无法确认同店 | 放弃酒店 | 记录失败，继续跑在途和携程 |
| 阿里同店但无大床有早餐 | 放弃酒店 | 记录失败，继续跑在途和携程 |
| 在途无法确认同店 | 放弃酒店 | 记录失败，继续跑其他平台 |
| 在途同店但无大床有早餐 | 放弃酒店 | 记录失败，继续跑其他平台 |
| 携程无法确认同店 | 放弃酒店 | 记录失败 |
| 携程同店但无大床有早餐 | 放弃酒店 | 记录失败 |
| 页面加载失败 / 登录失败 / 超时 | 标记技术失败，放弃酒店 | 标记技术失败，继续其他平台 |
| 解析疑似失败 | 暂停进入销售输出，需人工复核 | 标记需人工复核 |

## 五、失败类型

固定失败类型建议：

- `qingmao_no_main_rate`
- `competitor_no_same_hotel`
- `competitor_no_main_rate`
- `login_or_permission_failed`
- `page_load_timeout`
- `stale_page_or_wrong_date`
- `parser_suspected_failed`
- `platform_page_state_error`
- `unknown_technical_failure`

## 六、并发规则

现阶段不并发。

原因：

- 当前还在校准链路；
- 同一个 Chrome 调试窗口并发容易互相抢页面；
- 截图、状态、页面清理容易串；
- 失败原因不容易判断；
- 并发会增加旧页面、旧日期、旧酒店残留风险。

后续条件成熟后，再讨论半并发：

`青猫成功后 → 阿里和在途并发 → 两个都过了再查携程`

但前提是：

- 3 家校准测试稳定；
- 每个平台页面隔离清楚；
- 截图目录独立；
- 状态写入独立；
- 页面清理只清理本平台临时页；
- 失败原因能准确归类。

## 七、人工介入规则

人工只介入以下情况：

1. 截图肉眼能看到目标酒店，但系统说没命中。
2. 截图肉眼能看到大床、早餐、价格，但系统说没价格。
3. 门牌号写法变体太大，系统无法稳定判断。
4. 页面状态明显异常，例如旧日期、旧城市、弹窗遮挡。
5. 平台别名无法自动判断。
6. 详情页显示的信息不足，但列表页或人工路径可以确认同店。

其他情况尽量自动判断。

## 八、下一步

下一步先做 `3 家校准测试`。

不要直接进入 40 家。

3 家校准测试要验证：

- 青猫锁店是否稳定；
- 阿里、在途、携程的同店判断是否稳定；
- 主口径 `大床有早餐` 是否能稳定读取；
- 其他口径是否能顺手采集；
- 失败类型是否能准确分类；
- 截图和 finalUrl 是否足够人工复核；
- 当前平台顺序是否合理。
