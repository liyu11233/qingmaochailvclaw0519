# 青猫差旅比价工具第二版全栈技术路线图

日期：2026-05-20

## 1. 技术路线结论

第二版继续走本地优先架构。

核心形态：

- 用户本人电脑运行管理采集端。
- 用户人工登录四个平台。
- 系统附着或复用已登录浏览器窗口。
- 本地服务负责采集、保存、导出。
- 采集数据和截图证据保存在本地。
- 导出航班 + 酒店一体化离线网页包。
- 导出航班 + 酒店一体化 Excel。

不要第二版就做公网服务。

原因：

- 四个平台都有登录态、验证码、企业权限和风控问题。
- 云端采集会把问题放大。
- 离线网页包已经能满足销售演示。
- Excel 已经能满足会后复核。
- 本地采集能最大限度保留第一版稳定性。

## 2. 推荐技术栈

当前项目已经采用：

- React
- TypeScript
- Vite
- Express
- Playwright
- ExcelJS
- Vitest

第二版继续沿用。

不建议新增重型框架。

第二版真正需要的是模块拆分和数据模型升级，不是换技术栈。

## 3. 前端路线

### 3.1 管理采集端

管理端继续使用 React + TypeScript + Vite。

第二版新增页面能力：

- 四平台连接状态。
- 在途商旅验证状态。
- 航班采集进度。
- 酒店采集进度。
- 酒店集团进度。
- 当前批次航班和酒店统计。
- 一体化 Excel 下载。
- 一体化离线网页包下载。

管理端正式操作区建议保留：

1. 打开登录浏览器
2. 连接当前登录窗口
3. 验证在途商旅
4. 开始第二版完整真实采集
5. 导出 Excel
6. 导出离线网页包

高级验证区继续折叠：

- 只验证在途航班
- 只验证在途酒店
- 只采航班四平台
- 只采酒店候选池
- 只验证酒店多口径完整性
- 只采酒店其他 3 个口径

### 3.2 离线网页包前端

离线网页包不是管理端。

它是销售交付物。

页面结构：

- `index.html`：首页
- 航班页：国内航班、国际航班
- 酒店页：集团 tab
- 证据页或证据弹窗：打开平台截图

酒店页展示规则：

- 5 个集团 tab。
- 每个集团 8 家酒店。
- 每家酒店一张模块。
- 每家酒店推荐口径作为主价格区。
- 其他 3 个口径同页展示。
- 其他口径字号更小、颜色更弱。
- 不折叠。
- 不放次级表格。

离线网页包必须做到：

- 解压后直接打开。
- 不依赖本地 API。
- 不依赖网络。
- 相对路径引用截图证据。

## 4. 后端路线

后端继续使用 Express + TypeScript。

第二版后端职责：

- 管理采集任务。
- 控制操作锁。
- 调用四个平台采集器。
- 保存航班和酒店结构化数据。
- 保存截图证据。
- 生成离线网页包。
- 生成 Excel。
- 保存当前批次状态。
- 恢复最近可用批次。

建议接口分层：

- 平台验证接口
- 航班采集接口
- 酒店采集接口
- 完整采集接口
- 当前状态接口
- 导出接口

第二版主接口建议：

- 在途商旅验证
- 航班四平台采集
- 酒店候选池采集
- 酒店多口径采集
- 第二版完整采集
- 当前批次状态
- Excel 下载
- 离线网页包下载

## 5. 浏览器采集路线

### 5.1 采集方式

第二版继续采用：

- 人工登录
- 系统附着已登录浏览器
- Playwright 读取 DOM、页面元素、接口返回数据
- 截图作为证据
- 不把 OCR 作为主路径

四平台入口：

- 青猫差旅：已在第一版验证
- 携程商旅：已在第一版验证
- 阿里商旅：已在第一版验证
- 在途商旅：第二版先验证

### 5.2 平台适配器

建议将采集器按平台和业务类型拆分。

平台：

- Qingmao
- CtripBusiness
- Alibtrip
- ZTrip

业务类型：

- Flight
- Hotel

每个平台适配器只负责平台内部动作：

- 判断登录态。
- 搜索目标。
- 读取候选。
- 读取价格。
- 保存截图。
- 返回结构化结果或失败原因。

平台适配器不负责销售结论、不负责页面展示、不负责 Excel 排版。

### 5.3 在途商旅优先级

在途商旅是第二版第一风险点。

必须先验证：

- 登录后能否附着。
- 航班搜索是否稳定。
- 酒店搜索是否稳定。
- 页面结果是否能 DOM 读取。
- 是否存在强风控或跳转限制。

验证通过后，再接入完整流程。

## 6. 数据模型路线

第二版要从“航班批次”升级为“差旅比价批次”。

建议核心对象：

- CollectionBatch：采集批次
- Platform：平台
- EvidenceFile：截图证据
- FailureNote：失败记录
- FlightSample：航班样本
- FlightQuote：航班平台报价
- HotelGroup：酒店集团
- HotelBrand：酒店品牌
- HotelCandidate：青猫候选酒店
- HotelSample：最终入库酒店样本
- HotelPlatformMatch：平台酒店匹配结果
- RoomRateQuote：房型早餐报价

平台枚举：

- qingmao
- ctrip
- alibtrip
- ztrip

酒店口径枚举：

- king_no_breakfast
- king_breakfast
- twin_no_breakfast
- twin_breakfast

默认展示口径：

- 不固定为单一口径。
- 每家酒店按 4 个口径完整度动态选择。
- 同完整度时优先级为：king_breakfast > king_no_breakfast > twin_breakfast > twin_no_breakfast。

第二版有效酒店样本规则：

- 至少 1 个口径四平台完整。
- 4 个口径尽量采集，允许单个平台显示“暂无”。
- 缺失必须有留痕。

## 7. 酒店匹配路线

酒店匹配是第二版最难的部分。

不要用完全字符串相等作为唯一标准。

建议分三层：

### 7.1 酒店身份匹配

输入：

- 青猫酒店名
- 城市
- 商圈或地址
- 平台搜索结果酒店名
- 平台搜索结果地址

判断：

- 城市必须一致。
- 品牌或核心酒店名要相近。
- 地址或商圈相近时提高置信度。
- 不确定时放弃，不强行匹配。

输出：

- matched
- rejected
- uncertain
- reason

### 7.2 房型归一

输入：

- 各平台原始房型名
- 早餐文案
- 价格

归一：

- 大床
- 双床
- 无早餐
- 有早餐

允许差异：

- 标准、高级、舒适、商务等等级词可以不同。
- 但床型和是否含早餐必须一致。

### 7.3 留痕

Excel 必须保留：

- 平台原始酒店名
- 平台原始房型名
- 归一酒店名
- 归一床型
- 归一早餐
- 匹配结果
- 放弃原因

这样客户或内部人员能复核，不会变成系统黑箱。

## 8. 存储路线

第二版继续使用本地文件存储。

不建议现在引入数据库。

原因：

- 当前数据量不大。
- 采集批次以文件导出为主。
- 第一版已经有 `outputs/current` 和当前状态落盘机制。
- 加数据库会增加迁移和维护成本。

建议目录形态：

- 当前状态文件：保存最近可用批次。
- 批次数据目录：保存结构化 JSON。
- 证据目录：保存平台截图。
- 导出目录：保存 Excel 和离线网页包。

如果第三版要做历史批次管理、多用户协作、在线发布，再考虑 SQLite 或服务端数据库。

## 9. 导出路线

### 9.1 离线网页包

第二版离线网页包应生成一个 zip。

包内建议包含：

- `index.html`
- 静态样式文件
- 静态脚本文件
- 批次数据 JSON
- 航班截图证据
- 酒店截图证据
- Excel 文件副本或下载入口

注意：

- 所有路径必须相对化。
- 不能引用本机绝对路径。
- 不能依赖本地 Express 服务。
- 客户电脑离线打开也能看。

### 9.2 Excel

继续使用 ExcelJS。

第二版 Excel 要做成一个工作簿。

Excel 不内嵌网页截图图片。证据图片留在离线网页包的证据目录中，Excel 通过截图索引页、证据编号、相对路径和说明来指向证据。

建议 sheet：

1. 总览页
2. 航班汇总页
3. 酒店汇总页
4. 酒店集团明细页
5. 航班网页截图索引页
6. 酒店网页截图索引页
7. 内部留痕页
8. 失败记录页

公式口径：

- 青猫差额仍按青猫价格减竞品最低价。
- 青猫低于竞品时突出。
- 青猫高于竞品时明确显示贵了多少。
- 酒店推荐口径单独给结论。
- 其他 3 个口径尽量采集并保留明细。

### 9.3 交付物设计验证

Excel 和离线网页包的美观程度必须单独验证。

建议放在假数据一体化闭环之后、真实采集放量之前。

原因：

- 假数据最容易稳定复现版式问题。
- 真实采集放量前先定版式，避免后面边修采集边改设计。
- 这是面对客户的材料，不能只做功能正确。

设计验收内容：

- 离线网页包首页是否清楚。
- 酒店集团 tab 是否直观。
- 每家酒店推荐口径是否一眼突出。
- 其他 3 个口径是否弱展示但可读。
- Excel 是否像客户材料，不像后台导出。
- Excel 是否不嵌图但能定位证据。
- 表头、列宽、冻结窗格、颜色、公式是否可读。
- 页面和 Excel 是否通过用户确认。

## 11. 风险和兜底

### 风险 1：在途商旅不能稳定附着

处理：

- 先独立验证。
- 记录登录态要求。
- 必要时使用可见浏览器运行，但不保存账号密码。

### 风险 2：酒店同店匹配不稳定

处理：

- 城市必须一致。
- 品牌和核心酒店名相近。
- 不确定就放弃。
- 保留人工复核字段。

### 风险 3：房型口径不完整

处理：

- 至少 1 个口径四平台完整才进入销售主展示。
- 其他口径尽量采集，允许缺失。
- 缺失显示“暂无”。
- Excel 写明缺失原因。

### 风险 4：离线包体积变大

处理：

- 截图按证据目录保存。
- 优先压缩网页包。
- 不把无关调试文件打包。

### 风险 5：第一版航班稳定性被破坏

处理：

- 航班三平台逻辑先不重写。
- 在途作为新增适配器接入。
- 四平台开关和失败规则独立验证。
- 每阶段跑测试和构建。

## 13. 质量门禁

每个阶段完成后至少运行：

- `npm test`
- `npm run typecheck`
- `npm run build`

涉及前端页面变化时，还要打开本地页面检查：

- 页面无前端 console error。
- 按钮有 loading 和 disabled 状态。
- 错误提示用户可见。
- 酒店 tab 可点击。
- 离线网页包可打开。

涉及导出变化时，还要检查：

- Excel 能打开。
- sheet 完整。
- 公式存在。
- 没有内嵌截图图片。
- zip 能解压。
- 截图证据路径存在。
- 没有本机绝对路径泄漏到销售页。

涉及客户交付物设计变化时，还要检查：

- 离线网页包首页和酒店 tab 通过视觉检查。
- 大床有早餐视觉突出。
- 其他 3 个口径弱展示但可读。
- Excel 总览页、酒店汇总页、酒店集团明细页通过视觉检查。
- 用户确认页面和 Excel 可以面对客户。
